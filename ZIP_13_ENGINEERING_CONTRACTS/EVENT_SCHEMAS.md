# Event Schemas

Every event on the bus (Redis Streams, ADR-010) is wrapped in the envelope
below and validated against a JSON Schema before publish (`SYS_EVENT_SCHEMA_INVALID`
rejects the publish, `ERROR_CODES.md`). `payload` is event-type-specific;
everything else in the envelope is fixed.

---

## 1. Envelope

```json
{
  "event_id": "UUID, required — idempotency key, unique per event instance",
  "event_type": "string, required — e.g. DEAL_SCORED",
  "version": "integer, required — schema version of this event_type, starts at 1",
  "correlation_id": "UUID, nullable — ties a causal chain together (e.g. all events for one order)",
  "producer_service": "event_producer_service enum, required",
  "produced_at": "timestamptz, required, ISO-8601",
  "payload": "object, required — shape defined per event_type below"
}
```

Maps 1:1 onto `events` table columns (`DATABASE_SCHEMA.md` §13); `seq` and
`stored_at` are assigned by the Event Store Consumer on write and are never
set by producers.

Consumers dedup via `processed_events (consumer_service, event_id)`
(`DATABASE_SCHEMA.md` §18) — an event with an `event_id` already present for
that consumer is skipped (`SYS_DUPLICATE_EVENT`), not reprocessed.

Versioning: a breaking payload change bumps `version` and the event_type
keeps its name. Consumers must reject an unrecognized `version` for a known
`event_type` rather than guessing at the shape (`SYS_EVENT_SCHEMA_INVALID`).

## 2. Ingestion & scoring

### `LISTING_DISCOVERED`
Producer: `marketplace-connector`. Consumer: `deal-engine`.
```json
{ "product": "CanonicalProduct (CANONICAL_MODELS.md)" }
```

### `DEAL_SCORED`
Producer: `deal-engine`. Consumer: `telegram-bot`.
```json
{
  "deal_id": "UUID, required",
  "listing_id": "UUID, required",
  "marketplace": "marketplace_code, required — joined from listings/marketplaces at publish time (Deal Engine owns both tables); carried opaquely by every downstream consumer of this deal so no one re-derives it via a cross-service read",
  "score": "number, required",
  "score_breakdown": "object, required — see ScoredDeal in CANONICAL_MODELS.md",
  "detected_price": "integer paise, required",
  "reference_price": "integer paise, required",
  "discount_pct": "number, required",
  "expires_at": "timestamptz, required"
}
```

## 3. Deal interaction (Bot ↔ Deal Engine / Revalidation)

### `USER_INTERESTED`
Producer: `telegram-bot`. Consumer: `deal-engine`.
```json
{
  "deal_id": "UUID, required",
  "telegram_user_id": "UUID, required"
}
```
Never emitted for an expired deal — `STATE_TRANSITIONS.md` §1 "Tap-after-expiry" guard.

### `DEAL_REVALIDATION_REQUEST`
Producer: `telegram-bot`. Consumer: `revalidation-service`.
```json
{
  "deal_id": "UUID, required",
  "listing_id": "UUID, required",
  "correlation_id": "UUID, required — set to deal_id, so all revalidation rounds for one deal thread together"
}
```

### `DEAL_REVALIDATED`
Producer: `revalidation-service`. Consumer: `telegram-bot`.
```json
{
  "deal_id": "UUID, required",
  "listing_id": "UUID, required",
  "current_price": "integer paise, required",
  "in_stock": "boolean, required",
  "changed": "boolean, required — RevalidationResult.changed, CANONICAL_MODELS.md",
  "checked_at": "timestamptz, required"
}
```
If no `DEAL_REVALIDATED` arrives within 30s of `DEAL_REVALIDATION_REQUEST`,
the Bot times out and treats it as `PRICE_CHANGED` (`STATE_TRANSITIONS.md` §1,
`REVAL_TIMEOUT`) — it does not wait indefinitely or retry the request.

## 4. Order planning & allocation

### `PURCHASE_REQUESTED`
Producer: `telegram-bot`. Consumer: `order-planner`.
```json
{
  "order_id": "UUID, required — pre-generated by the Bot, becomes orders.id",
  "deal_id": "UUID, required",
  "listing_id": "UUID, required",
  "marketplace": "marketplace_code, required — carried forward from the DEAL_SCORED payload the Bot received, not re-derived",
  "telegram_user_id": "UUID, required",
  "requested_quantity": "integer, required, > 0",
  "unit_price": "integer paise, required — price at confirmation time"
}
```

### `ACCOUNT_ALLOCATION_REQUEST`
Producer: `order-planner`. Consumer: `account-service`.
```json
{
  "order_id": "UUID, required",
  "marketplace": "marketplace_code, required",
  "requested_quantity": "integer, required",
  "correlation_id": "UUID, required — set to order_id"
}
```

### `ACCOUNT_ALLOCATION_RESPONSE`
Producer: `account-service`. Consumer: `order-planner`.
```json
{ "allocation_plan": "AllocationPlan (CANONICAL_MODELS.md)" }
```
No response within 10s → `PLAN_ALLOCATION_TIMEOUT`, retried up to 3 times
by the Planner before the message is dead-lettered (`ERROR_CODES.md`).

### `PURCHASE_TASK_CREATED`
Producer: `order-planner`. Consumer: `purchase-agent` (one event per allocated account).
```json
{
  "purchase_task_id": "UUID, required",
  "order_id": "UUID, required",
  "account_id": "UUID, required",
  "listing_id": "UUID, required",
  "marketplace": "marketplace_code, required — tells the Purchase Agent which connector-specific checkout automation to run",
  "quantity": "integer, required",
  "max_price": "integer paise, required — checkout aborts if price exceeds this, see PURCH_PRICE_MISMATCH"
}
```

## 5. Purchase execution outcomes

### `PURCHASE_COMPLETED`
Producer: `purchase-agent`. Consumers: `order-planner`, `inventory-service`, `account-service`, `telegram-bot`, `ml-service`.
```json
{ "outcome": "PurchaseOutcome (CANONICAL_MODELS.md), success=true" }
```

### `PURCHASE_FAILED`
Producer: `purchase-agent`. Consumers: `order-planner`, `account-service`, `telegram-bot`, `ml-service`.
```json
{ "outcome": "PurchaseOutcome (CANONICAL_MODELS.md), success=false" }
```

Both events carry the same `purchase_task_id` correlation so the Planner can
match outcomes to `order_items` rows 1:1 and compute `fulfilled_quantity`
for the `EXECUTING -> COMPLETED|PARTIAL|FAILED` transition
(`STATE_TRANSITIONS.md` §2).

## 6. Account health

### `ACCOUNT_HEALTH_CHANGED`
Producer: `account-service`. Consumer: none required (audit/ML only —
`telegram-bot` consumes it only for Admin Dashboard health widgets).
```json
{
  "account_id": "UUID, required",
  "previous_status": "account_status, required",
  "new_status": "account_status, required",
  "previous_health_score": "integer, required",
  "new_health_score": "integer, required",
  "reason": "string, required — e.g. PURCHASE_FAILED delta, cooldown elapsed, admin action"
}
```
Emitted on every status or health_score change described in
`STATE_TRANSITIONS.md` §3, not just status transitions — ML training data
needs the score trajectory, not just the band crossings.

## 7. Dead-lettering

### `EVENT_DEAD_LETTERED`
Producer: whichever service exhausted retries. Consumer: none required
(observability only).
```json
{
  "original_event_id": "UUID, required",
  "original_event_type": "string, required",
  "consumer_service": "event_producer_service, required — which consumer gave up",
  "error_code": "SYS_DEAD_LETTERED, fixed",
  "attempt_count": "integer, required"
}
```
Moved to a per-consumer DLQ stream (`{event_type}.dlq.{consumer_service}`),
replay is manual via the Admin Dashboard, never automatic.
